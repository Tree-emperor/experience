```java
private RestResponse checkAndSaveTask(final MultipartFile file, final TaskInfo taskInfo) throws Exception {
    RestResponse response = RestResponse.success();
    // 构建责任链检查
    TaskCheckChain checkChain = new TaskCheckChain.Builder()
        .add(new DataResourceCheckStrategy(gisRestfulUtil, configDao))      // 数据资源检查
        .add(new MapRoadGridCheckStrategy(gisRestfulUtil, taskDao))         // 路网网格检查
        .add(new LicenseCheckStrategy(licenseDao, licenseBusiness, licenseFactory, cellQueryBusiness))  // 许可证检查
        .build();
    checkChain.check(taskInfo, response);
    
    if (response.getResultCode() == RestResponse.SUCCESS_CODE) {
        saveMultipartFile(file, taskInfo);  // 保存标注文件
        taskDao.saveTask(taskInfo);          // 持久化任务
    }
    return response;
}
```
校验内容详解:
检查策略	作用
DataResourceCheckStrategy	检查数据源是否可用、 polygon 覆盖的基站数量等
MapRoadGridCheckStrategy	检查路网网格划分是否正确、是否有冲突
LicenseCheckStrategy	检查许可证额度是否足够、场景是否符合

**为什么需要Pipeline配置**

原因1: 不同任务类型有不同执行流程
- 训练任务(TRAINING): 参数初始化 → 下载数据 → 智算训练 → 上传结果
- 推理任务(PREDICTION): 参数初始化 → 下载数据 → 智算推理 → 后处理(CBB/T0入库)
- 评估任务(EVALUATION): 类似推理流程

原因2: 配置解耦了业务逻辑
- 修改流程不需要改代码，只需修改配置文件
- 支持按RAT分裂、按模型分裂等不同执行策略
- 支持是否可解释(explainable)的差异化配置

原因3: 支持按Polygon分批
- 如果 isSplitByCell=true，一个任务可以按地理区域分裂成多个batch并行执行

2. 为什么要构建二级调度器？
二级调度器解决什么问题
背景问题: 
- 一个任务可能包含多个子任务（比如按地理区域分裂成N个batch）
- 每个子任务内部又有多个执行步骤（下载、训练、推理、上传等）
- 这些步骤之间有依赖关系，必须按顺序执行
- 同时任务可能失败、可能中断、可能需要重试
SecondScheduler的设计目的:
SecondScheduler（二级调度器）是单个步骤的执行单元，包含：


```java
SecondScheduler {
    String taskId;           // 子任务ID（智算侧返回）
    int batchNo;             // 批次号（按Polygon分裂时有多个batch）
    String invoke;           // 执行类型，如 "download", "intelligent", "upload"
    String rat;              // 无线接入类型（NR/LTE）
    int step;                // 步骤序号
    String status;           // 当前状态
    JSONObject model;        // 模型配置
}
```

关系:
TaskInfo (1)
  └── SubTaskInfo (N，按Polygon分裂)
        └── SecondScheduler (N，每步骤一个)
二级调度器的作用
1. 步骤解耦与可重试:

```java
// PipelineStrategy.createSecondSchedulers() 第338行
for (int index = 0; index < jsonArray.size(); index++) {
    SecondScheduler secondScheduler = JSON.to(SecondScheduler.class, object);
    secondScheduler.setTaskId(subTaskId);
    secondScheduler.setStep(atomicInteger.incrementAndGet());  // 步骤编号
    pipelines.add(secondScheduler);
}
```
每个步骤独立为一个 SecondScheduler，失败时可以从特定步骤重试，而不是从头开始。
2. 支持并行/串行执行:

```java
// TaskStatusExecutor.processSchedulersByBatch() 第206行
for (SecondScheduler secondScheduler : batchPipelines) {
    chain.handle(secondScheduler);  // 按顺序处理
    if (shouldBreakAfterStrategy(secondScheduler)) {
        break;  // 失败时停止后续步骤
    }
}
```
3. 状态追踪:
每个步骤有独立状态，便于精确定位失败环节：
- QUEUING - 排队中
- RUNNING - 执行中
- SUCCESS - 成功
- FAILURE - 失败
- PENDING - 等待中

## 定时调度处理任务总结

TaskStatusExecutor.schedule() 每分钟执行一次，处理的是子任务内的单个执行步骤：

---
处理内容
查询: 从数据库获取所有 SecondScheduler（二级调度器）中状态为 QUEUING 或 RUNNING 的记录

执行: 根据每个步骤的 invoke 类型，调用对应的执行器：

|invoke类型	|执行操作|
|--|--|
|download	|从SFTP/HDFS下载训练/推理数据|
|upload	|上传结果到存储|
|intelligent	|调用智算侧API，启动训练/推理任务|
|paramInit	|初始化任务参数|
|dataFunction	|执行数据处理（裁剪、转换等）|
|cbbAppDB	|CBB后处理结果入库|
---
处理逻辑（状态机驱动）
步骤状态流转:

```
QUEUING ──→ 获取执行器.execute() ──→ 执行成功 → 状态变为 RUNNING
                        │
                        └─→ 执行失败 → 状态变为 FAILURE
RUNNING ──→ 获取执行器.status() ──→ 智算侧完成 → 状态变为 SUCCESS
                             │
                             └─→ 还在运行 → 保持 RUNNING
```
核心就是: 
1. 已排队的步骤 → 触发执行
2. 执行中的步骤 → 查询状态
3. 失败的步骤 → 记录错误并中断
---
形象比喻
可以把 SecondScheduler 理解成流水线上的工位：
- download = 把原材料搬到工位
- intelligent = 加工产品
- upload = 把成品入库
- cbbAppDB = 贴标签归档

定时调度就是沿着流水线巡视：
- 看到待加工的 → 开工
- 看到加工中的 → 问一句"好了没"
- 看到坏了的 → 记录问题、停线

#### secondScheduler 初始状态？

完整流程：

```
用户提交任务
    ↓

    ↓
SecondScheduler.status = null（未设置）

taskDao.insertSecondSchedulers(secondSchedulers)

    ↓

```
所以初始状态 queuing 是在SQL插入时硬编码赋值的，而不是在Java代码中。

#### 任务执行 = 状态流转？

对的，SecondScheduler.status 是任务执行的唯一状态标识，定时调度器通过不断修改这个状态来推进任务执行。

------------

#### 为什么不用状态模式实现状态机？

如果用状态模式实现



```java
// 状态接口
interface TaskState {
    void handle(SecondScheduler scheduler);
    TaskState nextState();
}

// 具体状态
class QueuingState implements TaskState {
    @Override
    public void handle(SecondScheduler scheduler) {
        // 1. 检查前置条件
        // 2. 调用执行器
        // 3. 决定转换到哪个状态
    }
    
    @Override
    public TaskState nextState() {
        return new RunningState();
    }
}
class RunningState implements TaskState {
    @Override
    public void handle(SecondScheduler scheduler) {
        // 1. 查询智算状态
        // 2. 决定转换到哪个状态
    }
}

// SecondScheduler（Context）持有状态
class SecondScheduler {
    private TaskState state;
    
    public void process() {
        state.handle(this);
        state = state.nextState();  // 状态转换
    }
}

```
---
#### 策略链模式的优势
1. 自动状态匹配 vs 显式状态转换

|策略链模式|	状态模式|
|--|--|
|isEffective(scheduler) 自动判断|	显式调用 state.handle()|
|策略根据 scheduler.status 自动生效 |	需要外部判断当前状态再调用对应状态|

策略链更自动化：

```java
// 策略链：外部不需要知道有哪些状态
scheduler.process();  // 自动匹配到 QueuingStrategy
// 状态模式：外部必须知道当前是什么状态
if (scheduler.getStatus() == "queuing") {
    queuingState.handle(scheduler);
} else if (scheduler.getStatus() == "running") {
    runningState.handle(scheduler);
}
```
------------
2. 更容易中途拦截/中断

```java
// 策略链：可以在任意策略处中断
public void handle(SecondScheduler scheduler) {
    for (SchedulerStrategy strategy : strategies) {
        if (strategy.isEffective(scheduler)) {
            strategy.handle(scheduler);
            if (strategy.isBreak(scheduler)) {  // 可以设置中断条件
                break;
            }
        }
    }
}
```
比如 TimeoutStrategy 检查超时后设置 isBreak=true，后续策略都不会执行。

*状态模式很难实现这种"前置检查拦截所有后续状态"*

---

3. 扩展性：新增状态不需要修改现有代码

策略链符合开闭原则：

```java
// 新增 PendingStrategy，只需要：
strategies.add(new PendingStrategy());  // 添加到合适位置即可
// 现有策略不用改
```
状态模式需要修改所有状态类的 nextState() 判断；

---
4. 更适合批量处理
当前系统需要一次处理多个 SecondScheduler：

```java
for (SubTaskInfo subTaskInfo : subTaskInfos) {
    for (SecondScheduler scheduler : batchPipelines) {
        chain.handle(scheduler);  // 同一个策略处理多个对象
    }
}
```
状态模式的问题：每个 SecondScheduler 都要维护自己的状态对象，批量时状态对象太多，管理复杂。

#### 主任务并行问题


并行层级：

```
主任务A ─┬─ SubTaskInfo A1 ─┬─ batchNo=1 ─→ 串行 step by step
        │                  └─ batchNo=2 ─→ 串行 step by step
        │
        └─ SubTaskInfo A2 ─→ 与 A1 并行执行
                             
主任务B ─┬─ SubTaskInfo B1 ─→ 与 A1、A2 并行执行
        │
        └─ SubTaskInfo B2 ─→ 与 A1、A2、B1 并行执行
```
结论：
- 不同 SubTaskInfo：可以并行执行（CompletableFuture.runAsync）
- 同一 SubTaskInfo 内：按 batchNo 串行，同一 batch 内按 step 串行

结论：
- TASK_PERIOD_EXECUTOR_KEY 是全局锁，同一时刻只有一个调度器实例在执行
- 但调度器内部会并行处理多个 SubTaskInfo（来自不同主任务）
- 所以是：跨主任务串行获取锁，但并行执行各自的子任务

主任务有1个子任务，所有SecondScheduler成功时，	**主任务 → SUCCESS**；

PeriodTaskExecutor 和 TaskStatusExecutor  分别是周期任务触发器和任务状态查询触发器，两者都在同一个调度池中，每 30 秒被触发一次执行 schedule() 方法。

用户创建任务后，由 PeriodTaskExecutor 统一调度：

```text

SchedulerExecutor (应用启动时)
    ↓
每 30 秒触发一次 PeriodTaskExecutor.schedule()
    ↓
查询所有 task_period_info 记录
    ↓
根据 executionMode 区分：
  - executionMode = 0 → CycleTask 处理（周期任务）
  - executionMode = 1 → SingleTask 处理（单次任务）

```
无论周期任务还是单次任务，这个触发器都会发布事件：


```java
// PeriodTaskExecutor.processTaskPeriod() 第102-117行
private void processTaskPeriod(PeriodVariable variable) {
    TaskInfo taskInfo = variable.taskInfo;
    TaskPeriodInfo periodInfo = variable.periodInfo;
    int executionMode = periodInfo.getExecutionMode();
    
    // 根据 executionMode 选择对应的 PeriodTask
    for (IPeriodTask periodTask : periodTasks) {
        if (periodTask.effective(executionMode)) {
            periodTask.build(periodInfo, taskInfo);  // 执行构建逻辑
            break;
        }
    }
    
    // 统一的事件发布逻辑（不管单次还是周期）
    if (periodInfo.isNeedExecutor()) {
        applicationEventPublisher.publishEvent(new ModelTaskCreateEvent(this, periodInfo));
    }
}
// SingleTask - executionMode=1 时生效
public boolean effective(final int executionMode) {
    return executionMode == 1;  // 单次任务
}
public void build(final TaskPeriodInfo periodInfo, final TaskInfo taskInfo) {
    periodInfo.setNeedExecutor(true);  // 直接设为需要执行
    periodInfo.setEnable(false);       // 执行一次后禁用
}
// CycleTask - executionMode=0 时生效
public boolean effective(final int executionMode) {
    return executionMode == 0;  // 周期任务
}
public void build(final TaskPeriodInfo periodInfo, final TaskInfo taskInfo) {
    calculate(periodInfo, taskInfo);  // 计算是否需要执行
}

```

```
    ↓

    ↓
```

```
    └── calculate() → 判断 nextRunTime 是否到达

    ↓
[下一个周期] PeriodTaskExecutor.schedule() 再次触发
    ↓

    ...
```
